## What ships instead

palette, Midnight Teal `#0B2F2F`, Antique Gold `#D4AF37` and Ivory `#F9F6EF`: a lit arched window with a warm
horizon glow, soft lantern light and a faint lattice. No image, nothing to 404, nothing to
license, and no animation. The layout, copy and functionality are unchanged. The text sits on the
same dark base and scrims as before, and the e2e suite measures its contrast (WCAG AA).

## How the safeguard fails closed

1. **Build mode decides** (`src/design/artwork.ts`). The cinematic set is used only on the dev
   server (mode `development`) and in an internal review build (mode `art-review`). Any other
   build, including `npm run build`, resolves to CSS-only, and the image paths are folded out of
   the bundle. A dev-only `VITE_ART_MODE=css` can force CSS on the dev server (used by the
   `css-art` Playwright project); it can never turn the artwork on and does nothing in a build.
2. **`npm run build` runs the guard.** CI and the production deploy both run it, so no workflow
   changes are needed. `scripts/release-art-guard.mjs --prune` removes blocked files from
   `.output/public`, scrubs their entries from the asset manifest Nitro embeds in
   `.output/server/index.mjs`, then **fails the build** if anything blocked remains. It checks every
   generated file, including the SSR server bundle, for:
   - a blocked file name or name pattern,
   - content identical to a blocked file (SHA-256), so renamed or copied images are caught,
   - a text reference to a blocked image (JS, CSS, HTML, JSON, source maps),
   - a large inlined raster image (data URI),
   - the review-build stamp.
3. **The blocklist is pinned by hash** in `scripts/lib/art-manifest.json`. Deleting or renaming the
   source images does not unblock them. A unit test requires every raster image in `public/` to be
   classified (`blocked`, `unverified` or `approved`), so a new image cannot ship unreviewed.
4. **Review builds are stamped.** `npm run build:review` (and `npm run build:dev`) build with the
   artwork and write `REVIEW-BUILD-NOT-FOR-RELEASE.txt` into `.output/public`. Every non-review
   guard run rejects that stamp, and rejects a review bundle even without it because the image
   references are still present. A review build cannot pass `npm run release:check`.
5. **`npm run release:check`** re-runs the checks without modifying anything. Run it on any
   `.output` before `nitro deploy --prebuilt`.

## The `unverified` holding category

`art-manifest.json` also has an `unverified` list, currently empty, for files awaiting a decision.
A release build may not reference such a file and the guard warns while one is present. Moving a file
to `blocked` (as was done for the archway photos) makes it a hard failure.

## Enabling blocked artwork after written rights approval

Do not do this on your own judgment. Before any change you need, in the repository:

1. A written commercial-use statement from the rights holder (Emergent) covering the exact files,
   web distribution and AI-generated content, answering the six points in
   `QR-INT-005-HERO-ASSET-LICENSING.md`.
2. Owner sign-off on that record, with the SHA-256 of each cleared file.

Then, in one reviewed PR:

1. Move each cleared file from `blocked` to `approved` (and remove its name from `namePatterns` if a pattern covers it) in `scripts/lib/art-manifest.json`.
2. Change `src/design/artwork.ts` so a production build may use those files (keep CSS-only as the
   default for anything not cleared).
3. Update `scripts/lib/art-guard.test.ts` and `tests/e2e/74-css-art-fallback.spec.ts` accordingly.
4. Run `npm run build`, `npm run release:check`, lint, unit tests and the full e2e suite.

Until all of that exists, a release build ships CSS-only.
