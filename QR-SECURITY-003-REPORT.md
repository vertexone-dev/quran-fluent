### The zod decision (tested, rejected)

1. **Stay on 3.25.76 (kept).** The flagged code is not in the path the app uses and there are no array schemas.
2. **zod 4.6.7 imported as `zod/v3`: tested in a separate commit, rejected.** Local branch `experiment/qr-security-003-zod-v3-rejected` (`f2570f1`, not merged, not pushed). Type check, 260 unit tests, ESLint and build pass and `npm audit` reports 0 findings, but it **does not resolve the advisory**. I measured the actual behaviour with a 1,000,000-element invalid array against `.max(10)`: zod 3.25.76 `/v4` and zod 4.6.7 `/v3` both produce about 1,000,000 issues (about 0.4 to 0.7 s, hundreds of MB of heap); zod 4.6.7 `/v4` produces 1 issue in under 1 ms (and likewise for a constrained set). The fix is only in the v4 code, so the `zod/v3` route would silence npm without protecting anything. (Unconstrained arrays still accumulate issues in 4.6.7 `/v4`; the advisory concerns constrained collections.)
3. **Native zod 4:** would carry the fix, but breaks the type check (`ProfileMenu.tsx`: `.catch()` makes the `/auth` search params required at every `navigate` call) and needs route-by-route changes. Not a small update; not attempted beyond that finding.

## 3. Incident and cleanup: test user on the owner's local Supabase stack

**What happened.** `npm run test:e2e:setup` finds its target with `supabase status` run from the repository, which resolved to the owner's running local stack (project `wubzdnuwrhmrodwqkicg`) instead of my isolated one. It created one user there, `e2e-sec003@example.com`. Everything else I ran used the isolated stack.

**Cleanup (approved), with checks first:**

- The target was local: API `http://127.0.0.1:54321`, database in the local container `supabase_db_wubzdnuwrhmrodwqkicg`.
- Exactly one user matched the email: id `bd9b1993-d843-4bdc-af77-1173a05dc7ee`, created 2026-11-24 12:11:43 UTC, never signed in. The stack held 3 users; the other two (`e2e-repro-…`, `e2e-local-…`, created 7 and 4 November) were not touched.
- Dependent records: I listed all 29 foreign keys to `auth.users` and counted rows for this id. Five rows existed, all signup defaults: 1 identity, 1 profile, 1 learning preference, 1 role, 1 streak. Every other table had 0 rows. All those keys are `ON DELETE CASCADE` (one `SET NULL` table, empty).
- Deleted that single id through the auth admin API (HTTP 200). Afterwards: user count 2, no row for the id in `auth.users` or `profiles`, remaining users are the two original ones.

**Safeguard (commit `dda8d11`, `scripts/e2e/ensure-local-test-user.mjs`).** The script now refuses to run unless the API URL from `supabase status` equals the URL in `.env.test`, and accepts `E2E_SUPABASE_WORKDIR` to target a disposable stack explicitly. Verified: with the old situation reproduced (repo stack 54321 vs `.env.test` 56321) it refuses with a clear message and creates nothing (user count stayed 2); with `E2E_SUPABASE_WORKDIR` pointing at the disposable stack it works. CI is unaffected, because its `.env.test` is written from the same `supabase status`.

### The earlier 46/52 Android smoke run

Cause **not established**. The first run's UI dumps survive (`android-smoke/`); the console log and failed-check list do not. Evidence in the dumps: after the "Get started" tap the next dump (`01_home`) is byte-for-byte the same welcome screen as `01_launch`, so later steps ran from the wrong screen (the Learn dump shows the Reader). The four later runs and the final run (all 52/52) show Home at that point. That fits a missed or too-early tap right after a fresh install (the script waits one second), which would be a harness timing problem, but I cannot show that the app was healthy in that run, and one failing run in six is not ruled out as an app race. A useful next step is to run the suite repeatedly right after fresh installs with a longer wait after the tap and keep every log.
